# Design: the forge serving platform, from the tracer to production on kind

Status: reviewed (see q8.md), changes applied. Owner: the system's author. Scope: Passes 1 and 7.

## 1. Problem, users, constraints

**Problem.** Serve text completions from models we train, and from SmolLM2-135M-Instruct (a third-party model, labelled as such), behind an OpenAI-compatible API with API keys, rate limits, usage accounting, and latency and availability objectives, on one laptop running a single-node kind cluster; and make every request observable end to end, so an on-call person can tell a slow model from a slow gateway.

**Users.**

| User | Needs |
|---|---|
| API clients (scripts, the `openai` SDK, the agent of Pass 10, the load generator) | `openai-subset.v1.yaml`: chat and completions, streamed or not; 401/403/429 with `Retry-After` |
| The operator (on call: me) | dashboards, burn-rate alerts that fire within minutes, runbooks, a rollback that works |
| The course harness | milestones run through my entry points (`system.toml`), never through prebuilt binaries |

**Constraints.**

- One kind node inside Docker with 6 CPUs and 12 GiB; CPU-only inference.
- Python trains, Rust serves on candle, Go controls, and optional standalone C lessons explore kernels.
- Contracts are fixed by the course and vendored read-only (`contracts/`); I implement them.
- SLOs (the system's SLOs, scaled by the in-cluster calibration): TTFT p95 < 500 ms and TPOT p95 < 60 ms at 4 rps on SmolLM2-135M int4; availability 99.5% over 30 days.
- Non-goals: more than one node, GPUs, scaling the gateway out, isolation between tenants beyond keys and limits.

## 2. What is built

**Tracer (Pass 1).** A byte-level bigram trained in Python (`L0.0`), saved as safetensors, and served by a Rust engine (`L10.0`) that selects one row of logits from the checkpoint. A Go gateway checks a static key and passes SSE through without buffering (`gw.00`). Two Helm charts on kind and Jaeger all-in-one (`dep.00`, `obs.00`). The bigram stays servable for the whole course (D32), so the Pass 1 smoke test guards every later change.

**Serving platform (Pass 7).**

```
client --HTTP+SSE--> gateway (Go, 1 replica)
                     requestid > otel > recover > authn > ratelimit > cache > route > proxy > meter
                       | HTTP+SSE (data plane)            | gRPC EngineControl.Prefill
                       v                                  v
               decode engine x2 (Rust) <--gRPC tl.kv.v1-- prefill engine x1 (Rust)
                       |  candle tensors and model layers |
                       v                                  v
               Rust KV blocks and model layers     Rust KV blocks and model layers
all services --OTLP--> otel-collector --> Tempo (traces); Prometheus scrapes :9464 --> Grafana, alerts
```

## 4. Options: the engine topology on kind

Criteria, measured or estimated on the same inputs: 4 rps, 256 prompt tokens and 32 output tokens per request, int4 SmolLM2-135M. Speeds are from an in-cluster calibration benchmark scaled to the engine: prefill about 1,000 tokens/s per thread, a decode step of about 30 ms for up to 8 sequences on one thread.

| Criterion | A: one unified engine, 4 threads | B: two unified engines, 2 threads each | C: 1 prefill (2 threads) + 2 decode (1 thread each) |
|---|---|---|---|
| prefill time of one prompt | 256 / 4,000 = 64 ms | 256 / 2,000 = 128 ms | 128 ms |
| TPOT while a prompt prefills | chunked (`prefill_chunk = 128`): a step can carry one 32 ms chunk, so about 15 + 32 = 47 ms | about 20 + 64 = 84 ms: **misses 60 ms** | about 30 ms: decode never shares a step with prefill |
| KV moved per request | none | none | 256 x 23,040 B = 5.9 MB, about 6 ms on the node's loopback |
| one pod lost | everything lost | half the capacity | one decode: about half of the in-flight streams; prefill: all new requests (section 5) |
| pods and memory | 1 engine | 2 engines | 3 engines |
| what production readiness and the ops.01 incident need | no | no | yes ("prefill + 2 decode") |

**Decision.** Bring up with A (conformance and the first SLO run on the simplest topology), then run C in production. C keeps TPOT flat under prefill bursts (30 ms against a 60 ms target) and turns a pod loss into a partial failure. A stays one values change away (`role: unified`) as the rollback topology.

**What C gives up.** A third engine's CPU and memory (section 6); a KV transfer path with its own failure modes; TTFT about 70 ms worse than A (128 ms prefill plus 6 ms transfer against 64 ms); and a single prefill pod, which is the open question 1 below. I accept these because the TTFT budget still has 1.4x headroom (section 6) and the TPOT gain is the difference between meeting and missing that SLO under bursts.

The data plane stays HTTP end to end (D5): the gateway proxies the decode engine's SSE and only uses gRPC for `Prefill`. That keeps one conformance suite valid against every engine and the gateway alike.

## 5. Failure modes

| Failure | Detection | Degradation and mitigation |
|---|---|---|
| a decode pod dies mid-stream (incident `ops.01`) | `TTFTBudgetBurnFast` as the queue moves to the surviving decode; gateway failover logs; `tl.engine.active_sequences` drops | streams on that pod end with an SSE `error` event, never silently truncated and never spliced onto another engine; requests before their first byte are retried on the other decode (gw.05); the Deployment restarts the pod |
| the prefill pod dies | `TTFTBudgetBurnFast`, `EngineControl.Prefill` errors in gateway spans | the gateway routes new requests to a decode engine in unified mode (it can prefill locally, TTFT about 2x worse) until the pod is back; see open question 1 |
| the gateway pod dies | clients see connection errors; **no 5xx is recorded**, because the process that counts them is gone (open question 2) | Deployment restart in about 10 s; one replica by design (buckets, cache, ledger are per process) |
| KV pool exhausted | `tl.engine.kv.blocks{state="free"}` near 0, `tl.engine.queue.depth` rising | the scheduler preempts by recompute (L10.2); the bounded admission channel answers 429 with `Retry-After` (L10.5) instead of queueing without limit |
| one tenant floods | per-tenant panel, `tl.gateway.ratelimit.rejections` | RPM and TPM buckets per key answer 429 (gw.03); others keep their TTFT |
| collector or Tempo down | missing traces in Grafana | serving is unaffected: exporters drop spans once their bounded queue is full |
| Prometheus down | nothing fires: every alert is silent (open question 3) | none yet |
| bad config rolled out | pods fail readiness (`/readyz`), rollout stalls | `runtime.toml` is validated at startup against the schema; the values schema rejects literal secrets; `helm rollback` |

## 6. Capacity and latency budgets

**KV memory.** One token of one sequence holds a key and a value vector per layer and KV head: 2 x 30 x 3 x 64 x 2 B = **23,040 B**. The decode engines' pool is `kv_blocks = 2048` blocks of 16 tokens: 2048 x 16 x 23,040 = **754,974,720 B (720 MiB)**, room for **64** sequences of 512 tokens (512 / 16 = 32 blocks each), which is `max_seqs = 64`. The prefill engine holds blocks only until `Release`, so it gets 512 blocks (180 MiB).

**Concurrency.** End-to-end time W = 0.5 + 31 x 0.06 = 2.36 s at the SLO limits (the first token at TTFT, then 31 gaps), so by Little's law L = 4 x 2.36 = **9.44** requests in flight on average. Each holds 256 + 32 = 288 tokens = 18 blocks, so about 170 of 2,048 blocks (8%) are in use: the pool is sized for bursts and for the 64-way concurrency test, not for the steady state.

**Memory per node.** Engine: weights int4 135M x 0.5 B = 68 MB plus float32 embeddings and runtime, about 0.3 GiB, plus the KV pool: request 1.1 GiB per decode engine, 0.5 GiB for prefill. Gateway 128 MiB. Observability: Prometheus 1 GiB, Tempo 0.5 GiB, Grafana and the collector 0.25 GiB each. Total about 4.8 GiB of the 12 GiB node, leaving room for image builds and Tilt.

**TTFT budget (500 ms).** Gateway chain (auth, limit, route) about 2 ms. Queueing for the prefill pod: it is busy 4 x 256 / 2,000 = 51% of the time, and as an M/D/1 queue with a 128 ms service time the mean wait is 0.51 / (2 x 0.49) x 128 = 67 ms; I budget 3x the mean, 200 ms, for p95. Then prefill 128 ms, KV push 6 ms, first decode step 30 ms. About 366 ms: 1.4x headroom, the tightest budget in this design. If the load.02 report at 4 rps shows less, open question 1's second prefill replica halves the utilization.

**TPOT budget (60 ms).** One decode step of about 30 ms for up to 8 sequences per engine; at 9.44 in flight over two engines each runs about 5, so 2x headroom.

**Error budget.** 0.5% of 30 days is **216 minutes** of full outage, or 0.5% of about 10.4 million requests a month (4 rps). A fast-burn alert (14.4x over 1 h and 5 min) means an hour at that rate has spent **1/50** of the month's budget, and the whole budget would be gone in **50 hours**. A decode kill costs at most the streams on that pod, about 9.44 / 2 = 5 requests: noise against a budget of about 52,000 failed requests.

## 7. Rollout and rollback

- **Images and charts.** Images are built by CI (dep.05) and referenced by digest; no `:latest`. Engines roll with `maxUnavailable: 0, maxSurge: 1` and a PDB, so capacity never drops during a deploy. The gateway uses `Recreate`: two gateways writing one SQLite ledger on the same hostPath would contend, so I accept about 10 s of outage per gateway deploy (10 deploys a month is under 2 minutes of the 216).
- **Topology change (A to C).** Install the prefill and decode releases next to the unified one, then move traffic with the admin API (`PUT /admin/v1/routes`): 10% for an hour while the burn-rate alerts stay quiet, then 100%. Rollback is the same call with the old weights; the unified release stays installed for a day.
- **Contract migrations.** KV format v1 today; v2 (fp8) arrives through craft.13: readers first (decode engines accept v1 and v2, negotiated by the `fmt` field of `HasBlocks`), then writers (prefill emits v2), so no request ever meets a reader that cannot decode its blocks. The API moves to v2 through craft.14 with `Deprecation` and `Sunset` headers on v1.
- **Data.** `usage.db` follows `usage.v1.sql`; migrations are forward-only and additive, and the gateway pre-stop hook takes a `sqlite3 .backup` before an upgrade. Rolling back a schema change means restoring that backup, which loses the rows written since, so a schema change ships only after the code that reads both shapes.
- **Everything else.** `helm rollback <release> <revision>`; config changes roll pods through a checksum annotation on the ConfigMap.
