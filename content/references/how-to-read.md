# How to read these books

These books teach understanding through first principles and worked solutions. As code generation gets easier, the essential work is deciding what should happen, explaining why, testing the behavior, and validating it against the requirement. Read actively: a convincing explanation is a starting point for your own reasoning.

## Predict, reason, test, validate

| Step | What to do |
|---|---|
| Start from first principles | Name the problem, assumptions, constraints, and invariant before inspecting the implementation. Work a small case by hand. |
| Predict | Write down the expected output, state change, or failure before reading the next step or revealing an answer. |
| Reason | Explain the mechanism in your own words. Identify the assumption behind a design choice and what changes if it no longer holds. |
| Test | Choose a check that could prove your prediction wrong. Use boundary cases, counterexamples, or a controlled failure, and compare the observation with your prediction. |
| Validate | Decide whether the evidence supports the original requirement. State what remains untested, revise your explanation when needed, and try a changed scenario. |

For example, before reading a dynamic array's append implementation, predict what happens when its length equals its capacity. Explain why storage must grow before the write. Test an empty array, the capacity boundary, and one append beyond it; check that length increases and earlier values survive. Then ask whether the implementation's allocation and error behavior meet the caller's requirements. A passing ordinary append test alone does not answer that question.

Use the same method without code: derive an equation, check a small numerical case, change an assumption, and see whether the conclusion still follows. In a systems chapter, predict the behavior during a timeout or restart, then compare it with the traces or a controlled drill. Record your reasoning before the result so you can distinguish a prediction from an explanation invented afterward.

## Chapters and sections

A book is a sequence of numbered chapters, and each chapter is a sequence of sections: 5.3 is the third section of Chapter 5. A chapter opens with what it covers and what it assumes. Each section opens with a short introduction and its **Learning objectives**, works an example by hand, walks through the solution step by step, and ends with **Key terms**, a **Summary**, and **Review questions**. Answers to review questions are hidden until you reveal them, so try each one first.

On the website a chapter reads as one long page: keep scrolling and the next section follows. A section counts as read when you reach its end. This records your reading position, not your understanding.

## Code, math, and call-outs

Code listings name their language. Placeholders appear in angle brackets, such as `<system>`, and the system's own command-line tools in braces, such as `{ctl}`. Mathematics is set inline, like $\rho = \lambda / (n\mu)$, or in display blocks, and symbols are defined before they are used. **Warning** call-outs flag actions that can lose data or break a running system.

## Solutions and contracts

Nothing in these books is graded. Worked solutions expose the mechanism so you can inspect and challenge it. Read each one as a design under stated assumptions: explain the invariant it protects, compare the tradeoffs, and identify the evidence needed to trust it. Code generated by a tool needs the same scrutiny. The complete solution code lives in the repository under [`course/solutions/`](../../course/solutions/), and the interfaces every component implements under [`course/contracts/`](../../course/contracts/). Sections link to the exact files they discuss.

## Across books

Books link to each other instead of repeating material. When a section needs an idea from another book, it names that book in italics and links the section, for example [Vectors, matrices, row-major layout, and matmul](../courses/mathematics-for-computing/04-linear-algebra/01-vectors-matrices-and-matmul.md) in *Mathematics for Computing*.
