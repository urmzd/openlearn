# Heap top-k in C

The Python sampler in [Sampling and logit processors](../../build-an-llm/09-inference/01-sampling-and-logit-processors.md) in *Build Your Own LLM System* specifies top-$k$ by sorting every logit: `process_logits` orders all $V$ ids by (logit descending, id ascending) and keeps the first $k$. For SmolLM2, $V = 49152$. Sorting 49152 floats to keep 40 takes about $V \log_2 V \approx 770{,}000$ comparisons where roughly $V$ suffice.

This section implements the same ordering in C with about $V$ comparisons, using a binary heap of size $k$ that lives entirely in the caller's output buffers. It is an optional, standalone unit: no engine calls into this C code. Fixture files generated by the Python reference check that the two agree, and the Rust sampler in [Candle model runner](../../build-an-llm/11-serving/02-model-runner-and-sampler.md) is checked against the same fixtures independently.

You should know the binary heap from [A binary heap with lazy deletion](06-binary-heap-lazy-deletion.md), the chapter's first heap section, where sift up, sift down, and the array layout are developed. The C allocation and error support comes from [C runtime support and arena allocator with marks](../../build-an-llm/10-kernels/01-arena-allocator-with-marks.md), and [the growable array](01-growable-array.md) shows the same block discipline, although the heap itself allocates nothing. The contract is [`tinyllm/topk.h`](../../../../course/contracts/c/include/tinyllm/topk.h) under the rules in [`c/ABI.md`](../../../../course/contracts/c/ABI.md); the solution is [`topk.c`](../../../../course/solutions/c/src/ds/topk.c).

> **Learning objectives**
> - Define a total order on (value, index) entries that makes top-$k$ unique, and explain why NaN must be rejected while $-\infty$ must not.
> - Keep the best $k$ entries of a stream in a size-$k$ min-heap whose root is the threshold.
> - Show that scanning in increasing index resolves ties at the cut to the lower index with no extra code.
> - Turn the heap into best-first output with an in-place heap sort, without allocating.
> - Compare the heap's cost with a full sort and with quickselect.

## A total order on entries

The notation for this section:

| Symbol | Meaning | Type / shape |
|---|---|---|
| $x \in \mathbb{R}^n$ | the input values (logits), $x_i$ at index $i$ | `float[n]` |
| $n$ | number of values, $V$ for a logit row | `int64_t` |
| $k$ | number of values to keep, $0 \le k \le n$ | `int64_t` |
| $(v, i)$ | an entry: a value and its index | |
| $a \prec b$ | entry $a$ ranks below ("is worse than") entry $b$ | |
| $\mathit{idx}, \mathit{val}$ | the outputs: the kept indices and values, best first | `int32_t[k]`, `float[k]` |
| $h$ | the heap's current size, $h \le k$ | |

Top-$k$ is defined by an order, and values alone do not give one: two logits can be equal, and then "the $k$ largest" is ambiguous. The sampling spec (`spec/sampling.md` step 6) breaks ties by index, so define

$$(v_a, i_a) \prec (v_b, i_b) \iff v_a < v_b \ \text{ or } \ (v_a = v_b \text{ and } i_a > i_b).$$

Read it as "$a$ is worse than $b$". Indices are distinct, so for any two different entries exactly one of $a \prec b$ and $b \prec a$ holds: the order is **total**. The top-$k$ set is then unique: the $k$ entries that are worse than no more than $k - 1$ others. Listing it best first gives values in descending order and, among equal values, ascending indices.

### NaN and negative infinity

NaN breaks this. IEEE 754 makes every comparison with NaN false, so a NaN entry would be neither worse nor better than anything, and the result would depend on where in the array it happened to sit. The contract therefore rejects any NaN with `TL_EINVAL`.

$-\infty$ is different: $-\infty < v$ for every other value, and $-\infty = -\infty$, so it fits the order and ranks last. A logit masked by [constrained decoding](../../build-an-llm/09-inference/07-constrained-decoding.md) is $-\infty$, so rejecting it would break every masked request.

## The heap keeps the worst kept entry at the root

A **binary heap** is a complete binary tree stored in an array: the children of position $p$ are $2p + 1$ and $2p + 2$, and its parent is $\lfloor (p - 1)/2 \rfloor$. Here the heap property is: **no parent is better than its children**, so the root is the worst entry in the heap. That is a min-heap under $\prec$.

Why the worst at the root? The question asked of every new entry is "does it beat the weakest member of the current top $k$?" The algorithm scans $x$ once, keeping the best $h \le k$ entries seen so far in the heap:

1. While $h < k$, append $(x_i, i)$ at position $h$ and **sift it up**: swap it with its parent while it is worse than the parent.
2. Once $h = k$, compare $(x_i, i)$ with the root, the worst of the $k$ kept entries. If the root is worse, the new entry replaces it and is **sifted down**: swapped with its worse child while that child is worse than it. Otherwise the new entry is not among the $k$ best seen so far, and it is dropped.

The correctness argument is an invariant: after processing $x_0, \dots, x_{i}$, the heap holds exactly the top-$\min(k, i+1)$ entries of that prefix. It holds after step 1 trivially. In step 2, if the new entry ranks below the root, it ranks below all $k$ kept entries and cannot be in the top $k$; otherwise the root is now ranked below $k$ entries (the other $k - 1$ and the new one) and must leave.

Ties need no special code. The scan goes in increasing index, so a later entry with the same value as the root has a larger index: it is worse, and it stays out. The lower index wins the last place, as the spec requires.

### Sorting the result in place

After the scan, `idx` and `val` hold the top $k$ in heap order. A **heap sort** turns that into best-first order without extra memory: swap the root (the worst) with the last position, shrink the heap by one, sift the new root down, and repeat. The worst entry ends at position $k - 1$, the second worst at $k - 2$, and position 0 ends with the best.

### What it costs

Each of the $n$ values costs one comparison with the root. An entry that gets in costs $O(\log k)$ swaps, and the final sort costs $O(k \log k)$. In the worst case (an increasing array, where every value gets in) the total is $O(n \log k)$. For a logit row the order is close to random, and then the $i$-th value gets in with probability about $k / i$, so the expected number of insertions is about $k \ln(n/k)$. For $n = 49152$ and $k = 40$, that is about 280 insertions and 49152 root comparisons, against $n \log_2 n \approx 770{,}000$ comparisons for a full sort.

Quickselect (Hoare) finds the $k$-th value in expected $O(n)$, but it reorders the input, which the contract forbids (`x` is `const`), so it would need a copy of all $n$ values.

### Validate before the first write

The contract allows `0 <= k <= n` and requires `idx` and `val` untouched when it returns `TL_EINVAL`. So the function checks the ranges and pointers, then scans all of $x$ for NaN, and only then writes. A NaN at the end of the row is found after the whole scan; that costs one extra pass over $x$, which is cheap next to the heap work and keeps the error path simple.

## Working it by hand

Take $x = [1, 3, 2, 3, -1]$ (the logits of the sampling spec's worked example) and $k = 3$. Entries are written $(v, i)$, and the heap as an array, root first.

| Step | Entry | Action | Heap after |
|---|---|---|---|
| $i = 0$ | $(1, 0)$ | $h = 0 < 3$: append, nothing to sift | $[(1,0)]$ |
| $i = 1$ | $(3, 1)$ | append at 1; parent $(1,0)$ is worse, so no swap | $[(1,0), (3,1)]$ |
| $i = 2$ | $(2, 2)$ | append at 2; parent $(1,0)$ is worse, no swap | $[(1,0), (3,1), (2,2)]$ |
| $i = 3$ | $(3, 3)$ | full; root $(1,0) \prec (3,3)$: replace root. Sift down: children $(3,1)$ and $(2,2)$; $(2,2) \prec (3,3)$ and $(3,1)$ is not (equal value, smaller index), so swap with $(2,2)$ | $[(2,2), (3,1), (3,3)]$ |
| $i = 4$ | $(-1, 4)$ | root $(2,2)$ is not worse than $(-1, 4)$: drop | unchanged |

Now the heap sort. Swap root and position 2, giving $[(3,3), (3,1) \mid (2,2)]$; sift down in a heap of 2: $(3,1)$ is not worse than $(3,3)$, stop. Swap root and position 1: $[(3,1) \mid (3,3), (2,2)]$.

The result is `idx = {1, 3, 2}`, `val = {3, 3, 2}`. The two 3s tie, and the lower index comes first. The spec's own trace keeps ids 1, 3, 2 in that order.

## The interface

```c
/* tinyllm/topk.h */
tl_status tl_topk_f32(const float *x, int64_t n, int64_t k, int32_t *idx, float *val);
/* The k largest values of x[0..n) and their indices, best first; equal values by
   ascending index (and the lower index wins the last place). -inf is a value.
   TL_EINVAL, idx and val untouched, for k < 0 or k > n, a NULL pointer that would
   be used, or any NaN in x. k == 0 writes nothing. Allocates nothing. */
```

The C implementation is checked on its own. Python produces the reference fixture rows for parity; it does not load the C implementation.

## Building it step by step

Try to predict each step from the heap invariant before reading it.

1. **The answer must be unique,** so the order must be total. Values alone are not (ties), so the index breaks ties: the order $\prec$. Every comparison in the solution goes through one function, `worse`, so the tie rule cannot be applied in one place and forgotten in another.
2. **NaN cannot be ordered,** so it must be rejected; $-\infty$ can, so it must not be. The test is `isnan`, not `isfinite`.
3. **Rejection must leave the outputs untouched,** so every check, including the full NaN scan, runs before the first write.
4. **Deciding whether $x_i$ belongs to the current top $k$ only needs the worst kept entry.** That is the minimum under $\prec$, so the structure is a min-heap of size $k$: the root is the threshold, read in $O(1)$, replaced and repaired in $O(\log k)$.
5. **The heap needs $k$ slots, and the caller already provides $k$ slots** (`idx`, `val`). Building the heap there means no allocation, and parallel arrays mean every swap moves a value and its index together.
6. **The scan goes in increasing index,** so a later entry equal in value to the root is worse (larger index) and the strict test `worse(root, new)` keeps it out: ties at the cut resolve to the lower index with no extra code. In the worked example, $(3,3)$ enters because the root $(1,0)$ is worse, and $(-1,4)$ is dropped by one comparison.
7. **The output must be best first,** and the heap is in heap order. Repeatedly moving the root (the worst) to the end of a shrinking heap is a heap sort that leaves the worst last and the best first, in the same buffers.

### The order and the two repairs

`sift_down` picks the *worse* child because the parent must be no better than either child: promoting the worse child keeps that true for the other child too.

```c
/* 1 when entry (va, ia) ranks below entry (vb, ib): the total order. */
static int worse(float va, int32_t ia, float vb, int32_t ib) {
    return va < vb || (va == vb && ia > ib);   /* equal value: the larger index is worse */
}

/* Restores "no parent is better than its children" below position i. */
static void sift_down(int32_t *idx, float *val, int64_t size, int64_t i) {
    for (;;) {
        int64_t l = 2 * i + 1, r = l + 1, w = i;   /* w: the worst of parent and children */
        if (l < size && worse(val[l], idx[l], val[w], idx[w])) w = l;
        if (r < size && worse(val[r], idx[r], val[w], idx[w])) w = r;
        if (w == i) return;                        /* parent already the worst: done */
        /* swap value and index together: the arrays are one array of pairs */
        float tv = val[i];
        int32_t ti = idx[i];
        val[i] = val[w], idx[i] = idx[w];
        val[w] = tv, idx[w] = ti;
        i = w;
    }
}

/* Moves the entry at position i up while it is worse than its parent. */
static void sift_up(int32_t *idx, float *val, int64_t i) {
    while (i > 0) {
        int64_t p = (i - 1) / 2;
        if (!worse(val[i], idx[i], val[p], idx[p])) return;
        /* ... swap i and p, as above ... */
        i = p;
    }
}
```

### Validation

Validation comes first and covers everything a write could depend on. The `n > INT32_MAX` check exists because indices are stored as `int32_t`.

```c
tl_status tl_topk_f32(const float *x, int64_t n, int64_t k, int32_t *idx, float *val) {
    /* 1. Validate everything before writing anything. */
    if (n < 0 || k < 0 || k > n) { /* ... */ return TL_EINVAL; }
    if (n > INT32_MAX) { /* ... */ return TL_EINVAL; }          /* an index must fit idx[] */
    if (n > 0 && x == NULL) { /* ... */ return TL_EINVAL; }      /* NULL only when unused */
    if (k > 0 && (idx == NULL || val == NULL)) { /* ... */ return TL_EINVAL; }
    for (int64_t i = 0; i < n; i++) {
        if (isnan(x[i])) { /* ... */ return TL_EINVAL; }         /* isnan, not isfinite: -inf is a value */
    }
    if (k == 0) return TL_OK;                                    /* "off" is valid and writes nothing */
```

### The scan and the sort

The fill phase uses `sift_up` because entries arrive one at a time at the end; the replace phase uses `sift_down` because the change is at the root.

```c
    /* 2. Fill with the first k entries, then let each later entry replace the
     *    root when it ranks above it. A later entry equal to the root has a
     *    larger index, so it is worse and stays out: ties go to the lower index. */
    int64_t size = 0;
    for (int64_t i = 0; i < n; i++) {
        if (size < k) {
            val[size] = x[i], idx[size] = (int32_t)i;
            sift_up(idx, val, size);
            size++;
        } else if (worse(val[0], idx[0], x[i], (int32_t)i)) {  /* strict: equal is not enough */
            val[0] = x[i], idx[0] = (int32_t)i;
            sift_down(idx, val, k, 0);
        }
    }

    /* 3. Heap sort in place: move the worst to the end, shrink, repeat.
     *    What is left is best first. */
    for (int64_t end = k - 1; end > 0; end--) {
        /* ... swap positions 0 and end ... */
        sift_down(idx, val, end, 0);   /* the heap is now positions [0, end) */
    }
    return TL_OK;
}
```

The full solution is [`topk.c`](../../../../course/solutions/c/src/ds/topk.c).

### Why this design

The cost is one NaN pass plus one scan: $O(n)$ comparisons with the root, $O(\log k)$ per insertion, $O(n \log k)$ in the worst case and about $n + k \ln(n/k) \log k$ for random rows; the sort adds $O(k \log k)$. Memory beyond the output buffers is zero.

Each alternative gives something up. Sorting all $n$ is $O(n \log n)$, and it needs a copy of $x$ (the input is `const`) plus an allocation. Quickselect is expected $O(n)$, but it reorders its input, so it would need an $n$-sized copy; it still needs a sort of the $k$ survivors, and its tie handling depends on pivot choices unless the comparator is the same total order. A max-heap of all $n$ (heapify, then pop $k$) is $O(n + k \log n)$ but needs $n$ slots, while the size-$k$ min-heap fits in the caller's $k$ slots.

Two tradeoffs are accepted. The NaN check costs a second pass over $x$; in exchange no output is ever written on an error path. Parallel `idx` and `val` arrays mean two writes per swap, which is what the contract's output layout asks for anyway.

## Testing it and what can go wrong

A correct solution handles these cases:

| Case | Kind of check | Checks | Why it matters downstream |
|---|---|---|---|
| The hand example | unit, smoke | the worked example exactly | the definition of top-$k$ is the one the sampling spec uses |
| A tie at the cut goes to the lower index | boundary | $[5, 1, 1, 1, 1, 0]$, $k = 2$ keeps ids 0 and 1 | the ordering is deterministic |
| Equal values are listed by ascending index | boundary | all-equal input comes out in index order | top-p walks the kept ids in this order |
| $k = 0$ and $k = n$ | boundary | $k = 0$ writes nothing; $k = n$ is a full sort; $n = 0$ is fine | `top_k = 0` means off |
| $-\infty$ is an ordinary value | boundary | $-\infty$ ranks last, ties by index | masked logits from constrained decoding |
| NaN and bad $k$ are rejected without writing | boundary | NaN, $k > n$, $k < 0$, NULL pointers give `TL_EINVAL` and leave the outputs as they were | errors instead of garbage |
| Agrees with a full sort | property, differential | 300 random rows with many ties against `qsort` by $\prec$, every $k$ | heap shapes only random sizes reach |

The pitfalls mostly concern the order and the error path:

| Pitfall | Symptom | How the solution avoids it |
|---|---|---|
| replacing the root when the new value is greater **or equal** | a tie at the $k$-th place keeps the last tied index | the replace test is `worse(val[0], idx[0], x[i], i)`, strict under $\prec$ |
| comparing values only inside the heap | equal values come out in heap order, not index order | every comparison, in both sifts, goes through `worse` |
| no NaN check | the result depends on where the NaN sits | an `isnan` pass rejects the call before the scan |
| no `k > n` check | the heap writes past `idx` and `val` (ASan) | `0 <= k <= n` is checked first |
| forgetting the final sort | the right set in heap order; top-p (step 7 of the spec) walks it in the wrong order | step 3 heap-sorts the outputs in place |
| a max-heap (best at the root) | the root comparison drops the wrong entries | `sift_down` and `sift_up` keep the worst entry at the root |
| treating $k = 0$ as an error | a request with `top_k = 0` (off) fails | `k == 0` returns `TL_OK` after validation |
| writing before validating | a rejected call has already changed the outputs | all checks run before the first write |
| rejecting with `!isfinite` instead of `isnan` | every masked request fails | the check is `isnan`; $-\infty$ ranks last |

> **Warning:** `!isfinite(x)` looks like a safer NaN check, but it also rejects $-\infty$, and every request that uses constrained decoding masks logits to $-\infty$.

## Key terms

- **Total order**: an order in which any two distinct elements compare one way or the other; here, by value and then by index.
- **Min-heap under $\prec$**: a heap whose root is the worst entry, so it serves as the admission threshold.
- **Sift up / sift down**: repairs of the heap property after appending at the end or replacing the root.
- **Heap sort**: repeatedly moving the root to the end of a shrinking heap to sort in place.
- **Quickselect**: expected-linear selection of the $k$-th element by partitioning, which reorders its input.

## Summary

- Top-$k$ needs only a heap of size $k$: keep the best $k$ seen so far with the worst of them at the root, and each new value costs one comparison against the root, plus $O(\log k)$ swaps only when it gets in.
- The order is total: a smaller value ranks lower, and among equal values the larger index ranks lower. That one rule settles both who wins a tie at the $k$-th place (the lower index) and the output order of equal values (ascending index).
- NaN is rejected, $-\infty$ is a value: NaN has no place in any order, and a masked logit is $-\infty$ and simply ranks last.
- No allocation: the heap is built inside `idx` and `val`, and a final in-place heap sort leaves them best first.
- The C implementation and the Python reference agree on the kept set through shared fixture files.

## Review questions

1. Why is the root the worst kept entry rather than the best?
   <details><summary>Answer</summary>The question asked of every new entry is "does it beat the weakest member of the current top $k$?". Only the worst kept entry can be evicted, so it is the one that must be at hand in $O(1)$. A max-heap would put the best at the root and give no cheap way to find the entry to drop.</details>
2. Why does the replace test use `worse(root, new)` and not "new value greater than or equal to root value"?
   <details><summary>Answer</summary>With "greater or equal", a later entry tied with the root would replace it, so the last tied index would win the $k$-th place instead of the first. Because the scan runs in increasing index, a later equal value is strictly worse under $\prec$, and the strict test keeps it out.</details>
3. Why must the NaN scan finish before any write, even though it costs an extra pass?
   <details><summary>Answer</summary>The contract says a `TL_EINVAL` call leaves `idx` and `val` untouched. A NaN at the last position would be found only after the heap had already been built in the outputs. Scanning first is the only way to keep that promise without a temporary buffer.</details>
4. Why does the heap sort leave the outputs best first, when it moves the root to the end each time?
   <details><summary>Answer</summary>The root of a min-heap under $\prec$ is the worst remaining entry. Moving it to position `end` and shrinking fills the array from the back with entries in worst-to-better order, so position $k-1$ holds the worst and position 0 the best: descending value, ascending index among equals.</details>
5. About how many heap insertions does a random logit row of $n = 49152$ cause for $k = 40$?
   <details><summary>Answer</summary>The $i$-th value enters with probability about $k/i$, so the expected count is about $k \ln(n/k) = 40 \ln(1228.8) \approx 280$, next to 49152 root comparisons.</details>
